# Resume Engine｜岗位能力 × 经历证据 → 定制简历

本阶段的任务不是“把经历写得更厉害”，而是：

> **按岗位重要性排序用户已经真实拥有的能力证据。**

先读 `01_role_market.md` 与用户经历源，再执行。

## 1. 建立能力 × 经历证据矩阵

输出 `02_evidence_matrix.md`：

```md
# 岗位能力 × 经历证据矩阵

| 岗位能力 | 重要性 | 对应经历 | 证据强度 0-3 | 结果/证据 | 风险/边界 | 简历处理 |
|---|---:|---|---:|---|---|---|
```

证据强度：
- `3`：真实实践 + 明确结果/验证
- `2`：真实实践，有清楚动作但结果证据较弱
- `1`：弱相关、学习/探索、间接证据
- `0`：没有

规则：
- 0：不写成已具备能力
- 1：只能弱化表达，不能包装成强项
- 2–3：优先进入正文
- 能力重要性高但证据弱：进入“缺口/面试风险”，不是靠措辞解决

## 2. 选择最有价值的经历

排序依据依次为：
1. 与岗位 Core 能力的相关度
2. 业务 / 用户 / 工程结果强度
3. 能覆盖多少个 Core 能力
4. 证据可信度
5. 是否经得起面试追问

不要按时间机械排序，也不要为了“经历丰富”把弱项目塞满一页。

## 3. 岗位适配器

### 产品 / 项目型
强调：用户/业务问题、需求拆解、优先级、功能/流程、取舍、协作、验收、结果。

### 运营 / 市场 / 增长 / 销售型
强调：目标人群、渠道/策略、执行、转化链路、ROI/营收/活跃/留存、复盘。

### 数据 / 商业分析 / 策略型
强调：业务问题、指标、数据获取、分析方法、结论、决策影响。

### 技术 / 工程型
强调：技术问题、方案、实现/架构、性能/稳定性、工程结果。不要把产品原型能力包装成深工程能力。

### 设计 / 内容型
强调：用户/内容目标、创意问题、方案探索、关键取舍、作品/数据反馈、效果。作品集可能高于简历权重。

### 综合职能 / 管培型
强调：问题分析、主动性、协作、项目结果、商业判断、领导/组织证据。

## 4. STAR 不是标签，是组织逻辑

### 标准 STAR
适合需求驱动、过程判断重要、没有强量化结果的经历：
- S：业务/用户场景与原问题
- T：目标与本人范围
- A：拆解、判断、方案、取舍、协作、验证
- R：真实结果

### 反向 STAR
有强结果时用 `R → A → T/S`：先给降本、提效、增长、营收、转化、质量等结果，再说明怎么做到。

不要在简历里机械写 `S/T/A/R` 字母。

## 5. Action 必须体现判断

弱：
> 负责需求分析、设计方案、跟进开发。

强的结构应该能回答：
- 发现了什么问题
- 如何拆成可执行子问题
- 为什么选这个方案
- 放弃了什么
- 如何与他人对齐
- 怎么验收

动作日志不是能力证据。

## 6. 结果证据优先级

1. 业务结果：营收、成本、GMV、转化、交付、产能、留存
2. 用户结果：使用率、完成率、满意度、任务成功率
3. 质量/工程结果：错误率、修改率、通过率、性能、稳定性
4. 验证结果：用户测试、真实样本、负责人验收、比赛、Demo

没有第一层就使用下一层真实证据，不允许补出一个“更像商业成果”的数字。

任何亮眼结果都补可信度锚点：前提、对照、代价、质量是否下降、样本范围。

## 7. 产品 / AI 产品附加规则

产品经理正文尽量证明：
- 用户/业务需求拆解
- 功能规划与优先级
- 产品流程/交互/边界
- 需求文档或验收标准（真实做过才写）
- 数据/验收
- 跨设计/研发/业务推进
- 迭代

AI 产品经理额外证明真实做过的部分：
- AI 适用性与模型能力边界
- 模型/方案选型
- Prompt / Skill / Workflow
- RAG / Agent / 多模态（真实做过才写）
- AI 效果评测、Bad Case、回归验证
- 成本 / 质量 / 延迟权衡
- AI Coding

原则：`AI PM = 产品基本功 + AI 增量能力`。

## 8. PRD 与协作

PRD 是产物，不是凭空的能力标签。

- 正式写过 PRD：可以写
- 没写过，但做过功能定义、流程、交互说明、验收标准、需求边界：就写真实动作
- 不因为 JD 出现“PRD”就补一个不存在的 PRD

跨部门能力必须落在证据上，例如：与设计对齐交互、与研发定义接口/验收、与业务确认目标、与运营复盘数据。

## 9. 权责词审计

看到这些词自动检查：
`主导 / 独立 / 推动 / 负责 / 设计 / 搭建 / 上线 / 全链路 / 全面替代`

确认：
- 谁提出
- 谁决定
- 谁执行/开发
- 谁验收
- 用户本人真正做了什么

不清楚就降低表述强度。

## 10. 简历结构

若用户有模板：优先保留模板，不擅自换结构。

无模板默认一页优先：

```text
姓名 / 目标岗位 / 联系方式
个人简介（仅在能增加信息密度时）
实习经历
项目经历
核心技能
教育背景
```

一页过长时优先删：重复动作、技术流水账、弱项目、空泛技能；不要先删强结果、Core 能力证据、关键判断和真实验证。

### 个人简介
如果使用：`目标岗位 + 2–3 个核心能力 + 2–3 个强结果`。
不要堆“热爱、抗压、学习能力强、沟通能力强”。

### 技能栏
每一个技能词都必须能在正文或事实母库找到证据。技能栏不是 ATS 许愿池。

## 11. HR 5 秒测试

每段经历 5 秒内应能看出：
- 这是什么
- 为什么做
- 用户做了什么
- 结果是什么
- 与岗位有什么关系

看不出时：减少黑话、补业务实体、把最关键结果/动作前移。

## 12. 面试追问测试

对每个亮点追问：
- 数据怎么算
- 为什么选这个方案
- 替代方案是什么
- 本人 vs 团队分别做什么
- 谁拍板
- 怎么验收
- 怎么证明效果
- 最大失败是什么
- 重做会怎么改

答不上来时降低表达强度，不是帮用户发明答案。

## 13. 输出 `03_resume.md`

简历必须是可直接继续排版/转换 DOCX 的成稿，不要输出分析过程代替简历。

若用户提供 DOCX 模板且当前环境能可靠编辑，可另生成 DOCX；否则保留 Markdown，并明确未生成 DOCX，不要伪造文件。

## 14. 输出 `04_resume_audit.md`

至少包含：

```md
# 简历审计

## 岗位能力覆盖
## 强证据 / 弱证据 / 空白能力
## 事实与数字风险
## 权责风险
## AI贡献边界
## HR 5秒测试
## 面试追问风险
## 最终结论：pass / revise / blocked
```

### Gate C
只有 `pass` 或完成 `revise` 后才能进入当前岗位匹配。`blocked` 时说明缺什么事实，不强行继续。
