# Role Research｜公司池、JD 采样与岗位能力模型

本文件只负责阶段 1。目标不是“列一些公司”，而是用当前真实 JD 建立一个可用于简历与岗位匹配的岗位能力模型。

## 1. 输入

最少需要：
- 目标岗位名

可选但有影响时再获取：
- 实习 / 校招 / 社招
- 国家 / 城市
- 毕业时间或年级
- 行业偏好 / 明确排除项

先扩展岗位搜索词：

```text
目标岗位名
同义岗位名
常见英文名
相邻但仍属于同一岗位族的名称
```

不要把相邻岗位混进样本。例如“AI 产品经理”可以纳入 AIGC / LLM / AI 应用 / Agent 产品经理，但不能用算法工程师 JD 代替产品 JD。

## 2. 建立公司池

使用 **Control the in-app browser** 搜索目标岗位所在行业的企业格局。优先浏览器而非纯 HTTP 抓取，是因为招聘站常见 SPA、JavaScript 动态列表、登录态和交互式筛选；浏览器可以模拟真实用户查看渲染后的页面。遇到登录、验证码或权限限制时只标记 `Needs user`，不要绕过。

搜索目标岗位所在行业的企业格局，再建立三层公司池：

- 大厂：行业头部、平台型企业、大型集团
- 中厂：细分赛道头部、成熟成长公司、上市公司、独角兽
- 小厂：高成长初创、垂直团队、有真实产品和招聘需求的创业公司

默认每层尝试 5–10 家。行业本身较小时允许减少，不得为了凑数加入无关公司。

每家公司记录：

```text
公司名 | 梯队 | 主要业务/赛道 | 为什么与目标岗位相关 | 官方招聘入口 | 备注
```

“为什么纳入”必须指向岗位或业务，不接受“知名”“大公司”这种人类很爱写但毫无信息量的理由。

## 3. JD 采样规则

目标采集 12–20 个完整 JD；不足时最低尝试 8 个，且尽量跨至少 2 个公司梯队和 5 家不同公司。

防偏规则：
- 同一公司原则上最多计入 2 个高度相似 JD；
- 优先当前官方 JD，其次官方历史/缓存页面，再次可靠第三方完整 JD；
- 搜索摘要只用于发现，不进入核心统计；
- 每个用于能力建模的 JD 必须实际打开正文；
- 同一岗位重复镜像只算 1 个样本。

可以提前停止继续采样，仅当：
1. 已达到至少 8 个有效完整 JD；
2. 已覆盖多家公司；
3. 最近连续 3 个新 JD 没有改变 Top 核心能力集合，只增加措辞变体或低频加分项。

## 4. 每条 JD 的结构化抽取

每条记录：

```text

岗位名称：

地点：
官方/第三方：
岗位链接：

明确硬门槛：

工具/技术：

加分项：
业务场景：
```

只提取页面明确支持的内容，不把“最好有”改成“必须有”。

## 5. 能力归一化

把不同 JD 的同义表达归一到能力概念，而不是机械数关键词。

例：
- “需求洞察 / 用户需求分析 / 场景挖掘” → `需求发现与拆解`
- “跨团队推进 / 协同研发设计 / 项目推动” → `跨团队协作与推进`

每个能力保留来源 JD，防止模型凭印象发明“行业共识”。

## 6. 能力分层

输出 4 类：

### Core 5–8
高频且跨公司出现，直接影响岗位日常产出。

### Hard Gates
不满足可能无法投递或明显降级的硬门槛，例如学历、年限、语言、编程语言、资格证、可实习时长。

### Common Skills
常见但不是所有岗位都要求的工具 / 方法 / 行业能力。

### Plus
明确写作“优先 / 加分 / preferred”的条件。

不要只按出现次数判断 Core。满足下列任一也可进入 Core：
- 跨公司、跨梯队反复出现；
- 虽频次不最高，但显然是岗位产出的前置能力；
- 在岗位职责而非“加分项”里持续出现。

## 7. 分析梯队差异

必须单独写：
- 大厂更强调什么
- 中厂更强调什么
- 小厂更强调什么

只写样本支持的差异。若样本不足，标记“证据不足”，不要根据公司规模脑补文化神话。

## 9. Gate A

阶段 1 通过需要：
- 至少达到可解释的有效样本规模；
- 核心能力有 JD 证据；
- 不是被单一公司样本支配；
- 硬门槛与加分项已分开；
- 关键 JD 有可追溯链接。

否则继续研究或明确标记样本不足，不进入“确定版简历”。
