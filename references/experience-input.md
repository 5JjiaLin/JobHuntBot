# Experience Input｜经历来源与事实母库验收

本阶段只解决一个问题：**是否已经有足够真实的个人经历事实，可以安全进入简历生成。**

经历挖掘有两条路径，由用户自己选，Agent 不得默认把用户赶去另一个 GPT 会话。两条路径最终都收敛到同一份结构化、可检索的 **《个人经历.md》事实母库**。

---

## 1. 进入条件与分流

```
是否有可用的经历材料？
├─ YES：读取并核验 → 找岗位能力证据缺口 → 只补问必要问题（不强制重跑完整挖掘）
└─ NO ：给用户两个选择
        1. 在 GPT 里完成（复制 Prompt，带回 MD）
        2. 直接在 Codex 里完成（当前会话一问一答）
```

### 1.1 已有完整经历资料

用户已提供以下任意一项且内容足够：

- 已整理的《个人经历.md》事实母库；
- 详细旧简历 + 项目材料 / 实习记录；
- 作品说明 / PRD / 复盘 / 项目文档。

处理：

1. 先读取并核验；
2. 对照目标岗位核心能力，标记**岗位能力证据缺口**；
3. 只针对缺口补问一两个高价值问题；
4. 不强制重跑完整挖掘。

多份材料可以合并，但冲突处必须保留冲突，不得擅自选一个版本当真相。

### 1.2 没有经历材料：给两个选择

用户可见回复严格保持简单，类似：

> 接下来进入经历挖掘阶段，你可以选择两种方式：
>
> 1. **在 GPT 里完成经历挖掘** — 我会把完整的经历挖掘 Prompt 给你。你复制到 GPT，通过一问一答完成经历梳理，最后把生成的《个人经历.md》带回来，我再继续做证据匹配和简历。
> 2. **直接在 Codex 里完成** — 我现在就在这里按照同样的苏格拉底式流程，一次问你一个问题，逐步挖掘你的工作 / 实习 / 校园 / 项目经历，最后直接生成《个人经历.md》。
>
> 回复 1 或 2 即可。

不要在这一轮继续附加一堆问题。

---

## 2. 路径一：GPT（复制 Prompt）

用户回复 `1`：

1. 读取 `../assets/experience-miner-prompt.md`；
2. 把完整、最新的经历挖掘 Prompt 原样交给用户；
3. 告诉用户：复制到 GPT → 一问一答完成 → 最终输出《个人经历.md》→ 完成后把 MD 文件带回 JobHuntBot；
4. 当前 Phase 2 暂停在 Gate B。

没有拿到《个人经历.md》前，不得开始正式简历生成。用户带回 MD 后，读取并继续 Phase 2 → Phase 3。

---

## 3. 路径二：Codex（当前会话一问一答）

用户回复 `2`：Agent 直接在当前 Codex 会话完成经历挖掘。

### 3.1 第一问（固定）

**“你之前有过工作经历吗？实习也算。”**

据此分支：

#### 有工作 / 实习经历

优先挖：

- 工作
- 实习
- 兼职
- 正式职业经历

不要一开始就问校园活动。一段经历一段经历深挖；工作 / 实习经历挖完后，再补充有价值的：校园项目、比赛、课程项目、社团、学生组织、个人项目、创业尝试、研究、作品、志愿活动。

#### 没有工作 / 实习经历

直接进入校园 / 项目经历，可探索：

- 课程项目
- 比赛
- 社团
- 学生组织
- 个人项目
- 创业尝试
- 研究
- 作品
- 志愿活动
- 其他能够证明能力的真实经历

**不得因为“没有工作经历”就继续逼问工作经历。**

### 3.2 一问一答原则（苏格拉底式）

- **一次只问一个问题。** 不要一次发“请告诉我背景、目标、行动、结果、数据……”这种问卷式长问题。
- 每一问根据上一问回答决定下一问，优先选择**高信息增益**问题。
- 自然对话推进；不需要把 14 个经历骨架字段逐项机械地问用户。

底层经历骨架（内部理解用，不一次甩给用户）：

```text
Context / Trigger / Goal / Constraint / Problem / Decision / Action /
Collaboration / Artifact / Evidence / Outcome / Failure / Reflection / Transition
```

### 3.3 结束一段经历的标准

当以下内容都清楚即可停止，不继续考古低价值细节：

- 起因清楚；
- 场景清楚；
- 本人角色清楚（负责什么、不负责什么）；
- 核心行动清楚；
- 至少一个关键判断 / 取舍清楚；
- 结果清楚；
- 结果可信度清楚；
- 失败 / 局限清楚；
- 结束原因清楚。

### 3.4 何时生成《个人经历.md》

Codex 路径挖到以下程度即生成结构化《个人经历.md》：

- 覆盖目标岗位最可能使用的 2–5 段重点经历；
- 每段具备基本事实闭环（参考 §5 最低验收）；
- 横向识别出反复出现的行为 / 能力 / 决策模式。

它不是简历，不写成 STAR bullet；默认第一人称；包含时间线 + 真实场景 + 选择 + 判断 + 行动 + 协作 + 结果 + 证据 + 失败 + 转折 + 当前复盘。

---

## 4. 经历文件最低验收

对准备进入简历的每段重点经历，至少能回答：

```text
经历是什么 / 时间
业务或用户场景
原始问题或目标
本人负责什么
本人不负责什么
关键动作
至少一个关键判断或取舍
协作对象
产出物
结果
结果证据或数字来源
未完成 / 失败 / 局限
本人 / 团队 / AI 贡献边界
```

不是每段都必须有漂亮业务结果，但必须知道“最后发生了什么”。

## 5. 事实可信度标签

内部给关键事实标记：

- `A 强事实`：正式上线/真实使用/系统数据/财务数据/负责人验收/明确奖项等
- `B 边界事实`：历史对照、小样本、人工统计、内部测试、定性反馈、合理估算
- `C 背景事实`：动机、探索、失败、转折、兴趣来源
- `U 未确认`：记忆模糊、来源不明、材料冲突

`U` 不得直接写成简历强结论。

## 6. 数字核验

任何亮眼数字至少确认：

- 数字是什么口径；
- 来源是什么；
- 时间范围；
- 是本人结果还是团队结果；
- 是否估算。

例如“提升 30%”要知道：和什么比、怎么测、谁统计、大概还是精确值。

用户只记得“大概一半”时，写“约 50%”并保留估算边界，不制造 47.3% 这种看着很科学、实际上只是小数点 cosplay 的数字。

## 7. AI / 工具贡献边界

如果使用 ChatGPT、Codex、Claude、Gemini、Cursor、Copilot、Agent、自动化工具等，分开记录：

### 用户贡献
目标定义、约束、判断、取舍、验收、迭代要求、业务决策。

### AI / 工具贡献
代码生成、方案建议、文案生成、初版搭建、批处理、设计生成等。

禁止把“AI 生成的架构”直接写成“本人设计架构”；也不要把真实的目标定义和验收工作抹掉。

不能为了 STAR 完整性自动补：数字、结果、用户量、上线、测试、团队规模、AI 深度、协作对象。

- Demo ≠ 上线；
- 团队结果 ≠ 个人结果；
- AI 生成 ≠ 用户本人设计。

## 8. Gate B

只有当目标岗位最可能使用的 2–5 段经历具备基本事实闭环时通过。

若经历存在缺口：

- 缺的是高价值事实 → 只追问一个最影响简历可信度的问题；
- 缺的是低价值细节 → 标记未知，不阻塞；
- 核心能力完全没有证据 → 不编，留到能力缺口里。
