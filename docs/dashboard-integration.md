# Dashboard ↔ Workspace data contract

This document defines how the pipeline (skill), the dashboard and the optional
Feishu mirror share data. It exists so that any of the three can be changed
without silently breaking the others.

## 1. Single source of truth

```text
workspace/<target-role-slug>/jobs.csv
```

- The skill writes jobs there; the dashboard reads and writes the same files.
- Never create a second writable job pool (e.g. a CSV inside `dashboard/`).
- Everything else is derived: the dashboard is a view, Feishu is a mirror.

## 2. Job identity: `job_id`

Every job carries a stable `job_id`:

```text
jh- + sha256(company ␁ job_title ␁ canonical_job_url)[0:12]
```

- The canonical URL keeps identity-bearing query parameters (e.g. `?id=…` on
  `hr.163.com`) and strips only real tracking parameters — see
  [`scripts/job-id.js`](../scripts/job-id.js).
- All dashboard writes (`update-status`, `blocker/resolve`, `calendar/*`)
  address a job by `job_id`. Row position is never used as an identity, so
  sorting, inserting or re-running the pipeline cannot update the wrong row.
- Legacy compatibility: if a workspace predates `job_id`, the server falls back
  to `company + job_title`. This is a migration path, not a design choice.
- Regenerate ids with `node scripts/job-id.js --reindex <jobs.csv>` (backs up
  the file first).

## 3. Workspace layout

```text
workspace/<target-role-slug>/
├── 01_role_market.md          # phase 1 output
├── 02_evidence_matrix.md      # phase 2 output
├── 03_resume.md               # phase 3 output
├── 04_resume_audit.md         # phase 3 audit
├── 06_application_priority.md # phase 4 ranking
├── jobs.csv                   # single source of truth
├── application_log.csv        # submission records
├── follow_up.csv              # calendar / follow-up events
├── blockers.csv               # per-job blockers
└── config.json                # role metadata, feishu flag
```

## 4. Table schemas

The canonical column lists live in [`dashboard/workspace-schema.js`](../dashboard/workspace-schema.js);
`scripts/init-workspace.js` scaffolds empty tables from it and
`dashboard/server.js` reads/writes with it. The two must never drift.

Key columns the dashboard depends on:

| Table | Columns the UI reads |
|---|---|
| `jobs.csv` | `job_id`, `company`, `job_title`, `role_family`, `level`, `location`, `job_url`, `priority`, `status`, `resume_variant`, `blocker`, `next_action`, `notes`, `current_stage`, `submission_tier` |
| `follow_up.csv` | `date`, `company`, `job_title`, `event_type`, `status`, `time` |
| `blockers.csv` | `blocker_id`, `job_id`, `type`, `reason`, `status` |
| `application_log.csv` | `attempt_date`, `company`, `job_title`, `platform`, `status` |

Notes:

- The CSV dialect is all-quoted fields, `""` escapes, CRLF line endings, with a
  UTF-8 BOM. The reader strips *all* leading BOMs because stacked BOMs are a
  common artifact of external edits.
- `status` uses `Pending / Submitted / Offer / Rejected`; the two reserved
  values `排除-内容创作岗` and `已过期` mark excluded/expired rows.

## 5. Dashboard configuration

`dashboard/config.json` is **local-only and gitignored**; it is generated by
`npm run init:workspace` from [`dashboard/config.example.json`](../dashboard/config.example.json):

```json
{
  "workspace_dir": "../workspace/ai-product-manager",
  "target_role": "AI Product Manager"
}
```

`workspace_dir` is resolved relative to `dashboard/`, so the server does not
depend on the working directory it was started from.

If `config.json` is missing or empty the server still boots: it serves empty
tables, refuses writes with a clear message, and prints the init command.

## 6. Write API

All endpoints are `POST`, JSON only, loopback-only, and validated for `Host`
and `Origin`:

| Endpoint | Body | Effect |
|---|---|---|
| `/api/update-status` | `{ job_id, status }` | Sets `status` |
| `/api/blocker/resolve` | `{ job_id }` | Clears `blocker`, resets `next_action` |
| `/api/calendar/add` | `{ job_id, date, time, event_type }` | Appends a `follow_up.csv` row; stamps `current_stage` |
| `/api/calendar/update` | `{ followUpRowIndex, job_id, date, time, event_type }` | Updates one event + `current_stage` |
| `/api/calendar/delete` | `{ followUpRowIndex }` | Removes the event row |

`followUpRowIndex` identifies a row inside `follow_up.csv` (that table has no
separate event id yet); the *job* is always identified by `job_id`.

## 7. Change checklist

When touching the pipeline, the dashboard, or the schemas:

- [ ] Update `dashboard/workspace-schema.js` if any column list changed
- [ ] Regenerate `templates/workspace/*.csv` from the schema
- [ ] Keep every write addressed by `job_id`
- [ ] Run `npm run test:security`
- [ ] Verify the flow in a real browser on the demo workspace
  (`examples/demo-workspace/`), not on real data
